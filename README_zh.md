# NECOPN.DRV 逆向工程与 Python 渲染器 (NECOPN.DRV Reverse Engineering & Renderer)

本项目是对 NEC PC-9821 (Windows 95) 专属 MIDI 驱动 `NECOPN.DRV` 的一次深度逆向与行为复现尝试。项目通过 Python 结合底层 C++ 核心，实现了一套离线渲染方案，旨在尽可能还原当年实机的听感与声部调度逻辑。

> **🎯 项目状态**：目前在音高、包络、通道分配和鼓组行为上已基本完全复现实机效果（除软件 LFO 特性存在已知限制外）。

## 🏗️ 复现架构与核心说明

**1. 关于“双核心”的软件映射**
PC-98 真实硬件虽然搭载了 YM2608 (OPNA) 芯片，但官方驱动在软件层为了规避芯片特性和干扰，严格限制了单颗芯片只使用 CH0-CH2。因此，本项目在复现时采用了 **2 个核心实例 × 每核 3 个通道（共 6 声部）** 的软件架构，完美映射了原驱动的逻辑，而非硬件物理上的 12 声道。

**2. 为什么从 ymfm 换到了 fmgen？**
在初期开发中，本项目使用 `ymfm` 作为底层音频合成核心。但在后续与实机录音对比时，发现 `ymfm` 在某些长音延音（如 SR 值较低的音色）的表现与预期期望有偏差。为了追求更极致的实机听感，最终将底层封装替换为 `NP21/W` 模拟器所使用的 `fmgen` 核心（详见 `core/` 目录）。
*注：为了保持 Python 侧代码接口兼容，`necopn_core.py` 中的封装类名仍保留为 `YmfmCore`，但实际加载的是 `necopna_fmgen.dll`。*

## 📦 资源准备 (Required Assets)

**受版权限制，本仓库不包含任何原厂二进制文件或受保护的采样资源。** 运行前请自行准备：

1. **驱动文件 (`NECOPN.DRV`)**
   * **获取**：从日文版 PC-98 Windows 95 镜像或系统中提取。
   * **放置**：**直接将 `NECOPN.DRV` 放在 `player.py` 所在的根目录**即可，代码默认会在此处寻找（也可通过 `--drv <路径>` 参数指定）。
2. **原生打击乐采样 (`RHY` 文件夹)**
   * **获取**：你需要 6 个 16-bit PCM 格式的 WAV 文件，文件名必须严格为：`2608_bd.wav`、`2608_sd.wav`、`2608_top.wav`、`2608_hh.wav`、`2608_tom.wav`、`2608_rim.wav`。
   * **放置**：建议放在一个文件夹（如 `RHY/`）中。由于路径需自行管理，运行时**必须通过 `--rhythm-rom <文件夹路径>` 手动指定**，否则鼓组将静音。

## 🚀 快速开始

```bash
# 渲染为 WAV
python player.py example.mid -o output.wav --rhythm-rom ./RHY

# 导出为 VGM (旁支功能，可能存在兼容性问题)
python player.py example.mid -o output.vgm --vgm
🗂️ 关于 necopn_reverse/ (逆向副产品)
NECOPN_GM.wopn：这是逆向出的 128 个音色的 WOPN 包。请注意，它仅供可视化研究（如用 OPN2-BE 打开），并不参与本项目的实际渲染流程（Python 直接读取 .DRV 的 0x5510 偏移处数据）。

⚠️ 已知限制 (Known Issues)
虽然力求完美，但受限于时间和个人技术，本项目仍存在以下小瑕疵：

软件 LFO 噪音：当开启 --enable-lfo 参数时，软件 LFO 的高频相位刷新可能会导致音频出现轻微底噪。目前该特性默认关闭以保证听感纯净。

VGM 导出异常：通过 --vgm 导出的文件在部分严格校验的播放器（如 foobar2000 vgmplay）中可能无法发声。作为旁支辅助功能，目前暂未修复。

🔬 技术细节
音色解码：直接从 DRV 读取 64 字节记录，按 cs:0x1239 取反表进行硬件映射。

力度与包络：严格遵循 0x0BED 的算子掩码逻辑及硬件 SR/DR 机制。

Timer 节拍：836.5 Hz 的 Timer-A 驱动，处理逻辑精确对齐反汇编指令。
