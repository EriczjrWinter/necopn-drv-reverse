NECOPN.DRV 逆向工程报告
目标文件: NECOPN.DRV (Windows 95 PC-9821 MIDI 驱动程序)
SHA256: cae5234a9ca88ac51495a065e8b85e2a7e7a11d98d213b95fa056e10b542dae8
文件大小: 30,096 字节
目标: 在软件中实现与真实硬件 1:1 的音频行为复现。

1. 文件身份与架构
格式: 16 位 NE (New Executable) DLL。

段结构:

seg1: 初始化与 MIDI 事件分发（LibMain, MYFAIRLADY）。

seg2: WEP (Windows Exit Procedure)。

seg3: 运行时核心引擎（寄存器映射、音色装载、Timer-A 中断、软件 LFO）。

seg4: 数据段（硬件端口表、资源数据）。

硬件目标: 双 YM2608 (OPNA) 芯片。驱动程序将逻辑通道严格映射到硬件端口：

逻辑 FM 通道 0-2 → 第一颗 OPNA (端口 0x188/0x18A)

逻辑 FM 通道 3-5 → 第二颗 OPNA (端口 0x18C/0x18E)

注：驱动严格限制每颗芯片只使用 CH0-CH2，因此总复音数为 6 声部。

2. 音色库提取 (FMPARA)
位置: 文件偏移 0x5510，大小 0x2000。

结构: 128 个 GM 音色，每个固定 64 字节。

字段映射与取反: 驱动程序以取反形式存储包络参数。字段读取器 (seg3:0x11F8) 会应用 cs:0x1239 处的取反表。

AR, DR, SR = 0x1F - rec[n]

TL = 0x7F - rec[n] （注意：真实 TL 位于记录的 0x1B-0x1E 字节处）

WOPN 导出关键修正: 在导出为 WOPN 格式时，SL (Sustain Level) 和 RR (Release Rate) 绝对不能进行取反。如果错误地应用 0x0F - rec 规则，会将代表最大延音的 0 变成代表瞬间静音的 15，导致管风琴音色听起来像敲击木鱼。WOPN 格式在这两个字段上直接期望获取硬件原始值。

算子顺序: 驱动程序使用硬件槽位偏移 [0x00, 0x08, 0x04, 0x0C]。导出为 WOPN（使用 +0/+4/+8/+C 顺序）时，必须映射为 [0, 2, 1, 3]。

3. 移调机制 (FMOCTAVE)
位置: 文件偏移 0x7510（128 字节）。

行为: note += FMOCTAVE[program]（有符号字节）。

静音陷阱: 移调后，如果最终音符 >= 0x5C (92)（由于负数偏移导致无符号回绕），驱动程序会完全跳过 key-on 阶段（不写入 FNUM 和 0x28），但依然会分配并占用该声部。这会导致无声的音符白白窃取复音资源。

4. MIDI 事件层与通道分配 (seg1:0x04DE)
力度映射 (seg3:0x0BED): 力度通过 128 项查表 (level = 0x40 + v/2)，并与算法的载波算子掩码 (cs:0x0C55) 结合。调制器 (Modulators) 不响应力度。

抢音策略 (seg1:0x0058): 采用 4 轮查找分配。当 6 个声部全部满载时，会抢占 MIDI 通道号最大 的声部。如果当前请求的通道号低于受害者通道号，则该音符直接丢弃（低 MIDI 通道具有绝对优先权）。

鼓组 (通道 9/15): 映射到 YM2608 板载的 6 种节奏乐器。哑音音符（如 39, 60-81）被明确忽略。

5. 核心发现：包络的“慢速衰减档”
在与 NP21/W 实机录音进行波形对比时，发现了当前主流 ymfm 模拟器核心的一个严重缺陷。

缺陷本质: YM2608 的包络发生器在极低的 Sustain Rate (SR < 15) 下存在一个“慢速衰减档”。Nuked-LLE 和 fmgen 都通过检查 rate2 < 48 来实现该档位（将包络计数器门控在大约 3/16 的周期）。而 ymfm 缺失此档位，导致低 SR 音色（占 NECOPN GM 库的 85%，如弦乐、管风琴、Pad）瞬间衰减消失。

解决方案: 底层核心已从 ymfm 彻底切换至 fmgen（移植自 NP21/W），成功还原了长音延音，实现了与硬件的 1:1 匹配。

6. 软件包络与 LFO (seg3:0x0D59)
Timer-A: 配置为 0x0E3，频率约 836.5 Hz。用于驱动包络状态机。

LFO 推进频率的真实上限: `irq_poll` (seg3:0x0D27) 不是中断服务程序，而是 `MODMESSAGE` 下方的**轮询函数**。每次被调用时检查 YM2608 状态位，Timer-A 已溢出才 ack 并更新 LFO。因此 LFO 的实际推进频率 = `MODMESSAGE` 回调频率，而不是 Timer-A 的 836.5 Hz。在 Win95 的 `midiStreamOut` 下，这个回调频率通常只有 ~120 Hz（80-150 Hz 区间），Timer-A 的溢出大多被丢弃。

音色库的 `rate_word` 按 836.5 Hz 标定: 反汇编中 `rate_word = record[0x14..15]` 被直接乘入累加器，没有中间除法。这说明音色设计师按"驱动提供 836.5 Hz 时钟"设计，但实际回调频率远低于此。**设计意图与实机行为的历史不一致**，不是 bug，是 Win16 驱动调度机制的产物。等效复现方式是把 LFO 推进分频 7 倍（`836.5 / 7 ≈ 119 Hz`），对应 Python 侧的 `--lfo-divisor 7`（默认值）。

电磁噪音的真实根因（非相位重置）: 旧版本认为高频写 FNUM 会导致相位不连续——这是错的。`Operator::SetFNum` 只设置 `dp_`/`bn_` 并标脏 `param_changed_`，`pg_count_` 由 `KeyOn()` 清零，`SetFNum` 不重置它。真正的根因在 TL 计算的 `seg3:0x0F92-0x0FC8`：
- `idiv 0x7FFF` 后得到的商字节在 `xor ah, ah` 后被当作**无符号 0-255** 使用
- 若 `t1` 为负（`lfo < 0` 且 `trem > 0`），低字节落在 0x80-0xFF，汇编视其为 241-255 的大正数
- Python 旧实现错误地 `if t1 >= 128: t1 -= 256` 转成有符号，导致 `t2 = (t1 * b) // 0x7F` 变为负数
- `t2 &= 0xFF` 后 `s = t2 + b > 0xFF` 触发 `s = 0`，TL 突跳到最响（0 = 最大音量）
- 听感即"电磁噪音"，且目标若是 carrier 则直接表现为音量暴涨

修复: `_lfo_step` 的 TL 计算逐字节对照 `0x0F92-0x0FC8`，包括 `t1` 的无符号处理、`idiv 0x7F` 的正数路径、`s > 0xFF → 0` 的溢出判定。

Shape 1/3 相位修正: 方波/噪声 LFO 的相位判定依赖 `lfo_counter`，但该计数器按 836.5 Hz 递增而 `_lfo_step` 只按 120 Hz 执行。直接使用会让方波/噪声频率被放大 7 倍。修复方式是 `eff_counter = lfo_counter // lfo_divisor`，只在 shape 1/3 分支里使用，不影响 shape 0/2/4/5。

77. 未解之谜与限制
VGM 导出: 多芯片 VGM 流的分离在严格校验的播放器（如 foobar2000 vgmplay）中存在文件头兼容性问题。

软件 LFO: 电磁噪音、过度颤动的明显问题已解决（根因详见第 6 节）。但仍有若干未探明的细节，因此默认关闭:
- 包络状态机的 `rate_a` 起始延迟语义未验证（836.5 Hz 还是 120 Hz 基准），当前按 836.5 Hz 实现
- Shape 4/5 的 `lfo_value < 0` 截断逻辑与反汇编 `0x1060` 的逐字节等价性未完全验证
- `--lfo-divisor` 的默认值 7 来自"Win95 MIDI 回调 ~120 Hz"的合理估计，不是从反汇编直接确认的值。用户可用 `--lfo-divisor 5` 到 `14` 之间微调对齐自己手上的实机录音

MYFAIRLADY API: 扩展的私有 API（0x64-0x67 消息）未深度展开，因其与标准 MIDI 播放无关。
